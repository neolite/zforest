zforest — server-driven UI на Zig

Как устроен наш пайплайн и чем он отличается от htmx, Phoenix LiveView, Hotwire (Rails) и Laravel Livewire.

1. zforest: единый пайплайн «событие → граф → дерево → DOM-опы»

  • Состояние — на сервере: zefx-граф (события, сторы, derived) + модель приложения. У сессии свой граф и свой Dom-трекинг.
  • Три представления из одного дерева: SSR-страница, инкрементальный diff и SSE-снапшот строятся из одного buildView — рассинхрон невозможен по построению.
  • Транспорт асимметричный: клиент→сервер — обычный POST /action (ACK {rev}), сервер→клиент — SSE-поток patch-батчей. Никакого WebSocket.
  • Fine-grained: патчи — атомарные DOM-опы (text/attr/when/create/move), а в zmon bound-листья подписаны на сторы напрямую — обновление без rebuild дерева.
  • Кросс-таб fan-out: zboard бампает global_seq, каждая SSE-сессия поллит и догоняет патчами — как PubSub, но поверх той же patch-машины.

2. Как работают остальные

Phoenix LiveViewElixir

  • Состояние — assigns (плоская map) в процессе LiveView; реактивного графа нет — любой event → полный re-render шаблона → diff HEEx-фингерпринтов → HTML-патч.
  • Один WebSocket bidirectional: события и патчи в обе стороны. Клиент — «тупой» рендерер + morphdom.
  • Кросс-клиент — через PubSub вручную (вещание assigns всем процессам), не из коробки.

htmxHTML over HTTP

  • Чистый hypermedia: атрибуты hx-* на обычных элементах, сервер отдаёт HTML-фрагмент, htmx меняет DOM через swap.
  • Нет персистентного соединения и нет серверного состояния UI — каждый запрос stateless. Обновления только по действию пользователя.
  • 14 КБ JS, ноль фреймворка — но и ноль реактивности: нет derived-состояния, нет автовещания, нет fine-grained патчей.

Hotwire / TurboRails 7+ + Stimulus

  • SPA-навигация без JS-фреймворка: перехват ссылок/форм → fetch → подмена <body> или morph; Frames — точечная замена регионов.
  • Turbo Streams — ближайший аналог нашего SSE: сервер вещает HTML-фрагменты (append/replace/remove) по SSE/WS. Но фрагмент — императивная команда, а не diff от состояния: сервер должен сам решить, ЧТО прислать.
  • Stimulus — императивные JS-контроллеры для поведения; состояние по-прежнему в DOM/сессии, реактивного ядра нет.

Laravel LivewirePHP (+ Reverb для WS)

  • Концептуальный близнец LiveView: состояние компонента на сервере (public properties), клиент шлёт «действие» → сервер ре-рендерит Blade → HTML-diff (morphdom) → клиент патчит DOM.
  • Транспорт: AJAX (классика) или WebSocket через Laravel Reverb; синхронизация по checksum/snapshot.
  • «Реактивность» — computed getters, вычисляемые лениво при рендере. Графа зависимостей, settle-loop и derived-кэша нет — каждый render пересчитывает всё, что шаблон запросил.

4. Чем zforest отличается по сути

Все шесть систем делят одну идею: состояние и «что показывать» — на сервере, клиент — тонкий рендерер. Разница — в единице обновления и в наличии реактивного ядра.
  • vs LiveView / Livewire: они шлют HTML-diff — сервер рендерит шаблон и сравнивает разметку. Мы шлём DOM-опы, вычисленные из декларативного дерева: гранулярность ниже (отдельный text-оп на лист, when-оп на ветку), а в live-режиме (zmon) дерево вообще не пересобирается — лист сам подписан на стор.
  • vs htmx: htmx — чистый hypermedia без состояния; у нас полное серверное состояние + реактивность + автовещание, но ценой обязательного кастомного клиента (~200 строк, не фреймворк).
  • vs Turbo Streams: streams — это императивные HTML-фрагменты («вставь это»), сервер сам решает что слать. У нас патчи — производная от состояния: что бы ни изменилось в графе, diff сам вычислит минимальный набор опов. Не нужно писать «что послать» — только менять сторы.
  • Реактивное ядро (zefx): единственная система из шести с графом событий/сторов/derived и settle-loop. LiveView/Livewire пересчитывают всё при render; у нас derived-сторы кэшируются и уведомляют только зависимые листья.
  • Плата за это: кастомный протокол (ops вместо HTML), кастомный клиент, и сервер держит per-session DOM-состояние. LiveView/Livewire проще концептуально, htmx — радикально проще, но никто не даёт fine-grained реактивности «из коробки» на сервере.

5. Где мы на карте «зрелости»

stateless hypermedia          server-driven UI              fine-grained client frameworks
(htmx)                        (LiveView, Livewire, zforest)  (Solid, Svelte, React+fine libs)
     │                              │                                │
     └── нет состояния UI            └── состояние на сервере,        └── состояние на клиенте,
         и нет реактивности              тонкий клиент                  локальная реактивность
                                        │
                                        └── zforest: + реактивный граф,
                                            + DOM-опы вместо HTML-diff,
                                            + live bindings (zmon)

Итого: zforest — это LiveView/Livewire-подход, но с реактивным ядром и более низкой гранулярностью обновлений, без WebSocket и без клиентского фреймворка.
